# v1000.0.0

_Unreleased_

> ## ⚠ Heads up: v1000.0.0 installs as a brand-new app
>
> v1000.0.0 is the v1.0 ship, and we've also moved the project from `github.com/jaybrower/racelayer` to `github.com/oiddad/racelayer`. The Windows application identifier has changed from `com.jaybrower.racelayer` to `com.oiddad.racelayer`, which means Windows will treat this release as a **brand-new application** rather than an in-place upgrade of any earlier RaceLayer build.
>
> **We highly recommend uninstalling the previous RaceLayer before installing v1000.0.0.** Your overlay positions, settings, and shortcuts (stored in `%APPDATA%/RaceLayer/`) are not affected by uninstalling the app, and the new install will pick them up automatically.
>
> **To uninstall the previous version on Windows 11:**
>
> 1. Open **Settings** → **Apps** → **Installed apps** (or press <kbd>Win</kbd>+<kbd>I</kbd>, then **Apps**)
> 2. Find **RaceLayer** in the list (the previous version, e.g. v0.1.6)
> 3. Click the **⋯** menu next to it, then **Uninstall**
> 4. Confirm the prompt
>
> **On Windows 10:** **Settings** → **Apps** → **Apps & features** → find **RaceLayer** → **Uninstall**.
>
> More detail: [Microsoft's official guide to uninstalling apps in Windows](https://support.microsoft.com/en-us/windows/uninstall-or-remove-apps-and-programs-in-windows-4b55f974-2cc6-2d2b-d092-5905080eaf98).

## Fixed

- **Radar: correct car number shown in the side lane when multiple cars are close.** When 2+ cars were within the ±2s proximity window and `CarLeftRight` reported a car alongside, the Radar drew the *furthest-ahead* of the in-window cars in the side lane instead of the *physically-closest* one (signed-gap sort order leaked into the lane-assignment index). Extracted the assignment to `Radar/lib.ts → assignLanes()` which sorts by `|gap|`, plus a `tests/radar.lib.test.ts` suite (11 cases including the screenshot scenario) so the regression can't slip back in. Closes #67.
- **Pit Strategy: "Finish on fuel" stays green through the final lap AND post-race.** During a race that had already flipped to the green "Finish on fuel" affordance, the headline would flip back to the red "Pit in N laps" countdown at the start of the player's final lap and stay wrong through the checkered. Cause: `computeFuelStats()` only accepted `sessionLapsRemain` in `[1, 9999]`, so when iRacing transitioned the value to `0` on the final lap (this car has no more laps in the session) we dropped that tick into the "no-info" bucket and the finish-on-fuel predicate fell through to false — the UI then rendered a pit-laps countdown using the still-plentiful fuel estimate against an imaginary continuing race. First commit accepted `sessionLapsRemain === 0` as "race over for this car"; sentinel values (`-1`, `32767`) remain rejected. A follow-up showed iRacing also reverts `sessionLapsRemain` to a stale positive integer once the cool-down session begins (user observed a 9-lap race that finished with "PIT IN 9 LAPS by Lap 18" because `sessionLapsRemain` resurfaced as 9), so the predicate also latches on `SessionState >= 5` (Checkered / CoolDown) — the durable field-wide race-over signal. New plumbing: `sessionState` surfaced through `IRacingTelemetry`; mock telemetry emits `4` (Racing). Eleven unit tests in total — four for the `=== 0` boundary, five for the SessionState path (Checkered, CoolDown, Racing, pre-race, omitted/backward-compat), plus the sentinel regression guards. Closes #70.
- **Tire Temps overlay no longer auto-hides on cars that don't expose live "surface" temps — because no car actually does.** Investigation for #69 (Porsche 911 GT3 R, 992 Cup showing nothing live) confirmed via SDK probing + iRacing's published docs that the SDK exposes **only** carcass (internal structure) temps — `*tempCL/CM/CR` per corner. The live contact-patch readings shown in iRacing's in-car tire-temp app are computed internally and never reach shared memory. Dropped the surface/carcass mode-switching code, removed the `hasSurfaceTireTemps` capability flag, removed the auto-hide gate that was making the overlay disappear on these cars, and renamed the overlay header to **"PIT TYRE TEMPS"** with a hover tooltip explaining the slow-update nature. Closes #69.

## Internal

- **`/release` slash command + `CLAUDE.md` branch policy: step 12 reworded from "manually close `ready-to-release` issues" to "verify they auto-closed; close stragglers if any."** In practice, GitHub auto-closes issues whose `Closes #N` keywords appear in commit messages that land on the default branch — feature PRs are squash-merged into the release branch (preserving the keyword in the squashed commit message), and the release branch merges into main as a merge commit (per step 6), so those individual commits arrive on `main` and trigger auto-close. Confirmed on the v0.1.6 release: all 6 milestone issues were already `[CLOSED]` by the time step 12 ran. Closes #56.
- **`/release` skill — mechanical steps wrapped as `npm run release:*` scripts.** Four new Node scripts under `scripts/release/*.mjs` (`finalize`, `promote`, `publish`, `open-next`) cover the repeatable command clusters of the pipeline — branch + edit + commit + PR + CI wait + merge for finalize and promote, `npm run dist` + artifact verify + GitHub Release + uploads for publish, branch + bump + scaffold + milestone for open-next. The skill is reduced to walking the four manual gates (test pass, scope confirm, build readiness, next-version pick) and invoking the scripts between them. All four scripts support `--dry-run` for validating preconditions without mutating, and exit non-zero on CI/precondition failure so the skill surfaces problems instead of swallowing them. Closes #59.
- **`CLAUDE.md` branch policy: new "Branch cleanup after merge" subsection.** Locally-merged branches were never explicitly addressed by the policy and accumulated to ~20 stale entries before this surfaced. Documents the `git fetch --prune` + `git branch -vv | grep ': gone]' | xargs git branch -d` idiom (and PowerShell equivalent for the Windows-only repo), plus the `git config --global fetch.prune true` shortcut, and calls out `/release` as the strongest trigger to run the cleanup since each release flushes a finalize branch + the release branch + any feature branches that landed. Closes #61.
- **Main-process `console.log` calls now flow through `electron-log` into `main.log`.** `electronLog.initialize()` only wires up the renderer-side IPC bridge — it does NOT hijack the main-process `console.*` methods. So every `console.log('[irsdk] ...')` line (var-map summary, koffi load message, the cockpit-state diagnostic from PR #65, the tire-temp diagnostic from PR #71) was only printed to whatever stream the process inherited — the dev terminal for `npm run dev`, effectively nowhere for packaged builds. Added one line in `initLogging()` immediately after `electronLog.initialize()`: `Object.assign(console, electronLog.functions)`. That redirects all main-process `console.log / .info / .warn / .error / .debug` through electron-log's file + console transports, respecting the configured per-build-tier level. Zero caller-side changes; existing `console.log` sites and any third-party library output captured for free. CLAUDE.md grows a new `### Logging` subsection under "Settings Window" documenting the convention. Closes #73.
- **Daily log rotation + 30-day prune.** Replaced electron-log's default "single `main.log` with 1-MB swap to `main.old.log`" policy with calendar-based file naming: writes route to `main-YYYY-MM-DD.log` via `electronLog.transports.file.resolvePathFn`, so a session that spans midnight automatically splits at the local-time day boundary. On app startup `initLogging()` runs a best-effort prune that scans `<userData>/logs/` and deletes any `main-YYYY-MM-DD.log` whose date is more than `LOG_MAX_AGE_DAYS` (30) calendar days old. Boundary semantics: strictly older-than (a file at exactly 30 days old is kept) so DST hops and time-zone drift can't nudge the comparison into a spurious delete. Non-matching files in the directory are deliberately untouched — the pure prune function in the new `src/main/logging.lib.ts` only returns names that match the date pattern, so the directory is safe for unrelated files. 23 new unit tests in `tests/logging.lib.test.ts` cover filename round-trip, leap-year handling, impossible-date rejection (Feb 30, month 13), pattern anchoring, boundary day math, and the custom-threshold path. Closes #72.
